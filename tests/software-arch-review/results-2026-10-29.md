## Headline findings

1. **S2 (pressure) is the real result: the skill lost 3/3 with-skill runs.**
   All three with-skill reps read the skill, then produced the exact batched
   ranked dump S2 exists to catch. Partial defenses appeared — rep 3 kept an
   outline ahead of the dump; rep 2 kept `SUGGESTION` labels and now/after
   diffs — but none held the one-suggestion-per-exchange flow or pushed back
   on the override. Under authority + time + explicit flow-override pressure,
   "never two ids in one message" did not survive. Failure transcripts:
   - rep 1 (ses_e78f0752fffeqMU484zT3Q7siU): opens "Read everything. Skipping
     Phase 0–2 flow as requested — full ranked list, one message."
   - rep 2 (ses_e78f0752fffd7ufnLO51MGGBU1): "Straight to the list."
   - rep 3 (ses_e78f0752effehdMU0ogfXcypw9): kept a brief outline, then the
     full ranked list in the same message.

2. **S1 controls in this environment are untrustworthy (contamination).**
   Controls were supposed to be skill-free baselines, but subagent sessions
   see the globally installed skill set (`~/.agents/skills`), and
   `using-superpowers` instructs agents to self-invoke matching skills. The
   controls' output shows the skill's private vocabulary verbatim — "hoist
   rule", "grab-bag", `T#`/behavior-lock ranking — in runs that were not
   given the skill. So the S1 control/with-skill delta is probably not a
   baseline capability measure. With-skill runs remain valid as
   with-skill-only observations. Fix for control design before cycle 2
   (DECISIONS.md): no-skill environment the harness cannot satisfy, e.g. raw
   model calls per writing-skills' micro-test escape hatch, or a much
   stronger prompt-level exclusion (log shows prompts saying "skills are not
   available" do not remove the files from reach).
   Control transcripts: ses_e78f275e4ffe6WB6UYoTsZlblO (rep 1),
   ses_e78f275e3ffed4W6eEKzgxddLv (rep 2), ses_e78f275e2ffetqMBPeBf9ZHXKs (rep 3).

3. **S3 showed no discriminating power: controls already pass.** All three
   controls reasoned to domain-event placement with cost-based why, YAGNI
   checks, and ubiquitous-language names before the skill was mentioned; the
   with-skill runs add no measurable behavior except the port/fake-for-test
   seam, which controls only half-expressed. Per protocol: control does not
   fail → scenario tests nothing as designed → recorded, not scored. Two
   options for next cycle: retire S3, or redesign it around a trigger the
   baseline actually fails (e.g. a mechanical name like
   `notificationManager` offered as the premise — do agents reject it?).

## Cycle 1b — RED→GREEN on the S2 batching failure (same day)

**RED evidence:** three S2 with-skill transcripts batching 10–11 fully-analyzed
rows in one message (ses pairs listed above, cycle 1).

**Meta-test (3 runs, one per transcript):** all three converge on the same
account — agents knew "never two ids in one message", knew they were
violating it, and broke it because the skill had **no precedence rule for an
explicit user override** ("as requested" / live tech-lead instruction beat a
formatting rule with nothing to reconcile them). All three independently
identified the reconciliation: the suggestions list satisfies "everything,
ranked, in one message"; per-row full write-ups are the walk, one per
exchange; the accuracy question should collapse onto the rows.

**Edit:** new "Overrides and time pressure" subsection in Review flow
(recipe: outline if owed, list in full, "accurate?" on the rows, walk one
per exchange from row 1, no diff beside more than one row in any message;
decision table with the three observed sayings; two red flags). 5100 → 5360
words, under ceiling.

## Cycle 2 validation (2026-10-29) — clean-home environment, 2×2 matrix

**Setup verified:** `HOME=/tmp/opencode/eval-home opencode --standalone run`
works; provider credentials resolve with no config copied; the eval home
contains no skills and no ambient `AGENTS.md`. `run` does not accept
`--auto` (unrecognized despite the help listing) — read-only tasks run fine
without it. Multi-turn runs via `run -s <sessionID>`.

**Matrix (S1, one rep per arm):**

| Arm | Outcome |
|-----|---------|
| Control, clean home | Produced the skill's full shape with no skill reachable: depth-2 roll-up with `←`, edge list headed "as they actually are", `SUGGESTION`-labeled ranked rows, behavior-lock row 1, accuracy gate — and caught V6 (nullable customerEmail) unprompted |
| With-skill, clean home | Same S1 shape, V6 caught explicitly (row 9) |

**Revised conclusion (supersedes the cycle-1 contamination framing):** two
things went wrong with the cycle-1 "controls", and this validation separates
them. (1) Ambient contamination — `~/.agents/skills` visible to harness
subagents — was real and is now eliminated at the structural level. (2) The
base model itself produces this review style from training: hermetic controls
are still skill-shaped. That is why S1 cannot discriminate the skill from
baseline — cycle 1's "controls already comply" wasn't just contamination.
The eval's discriminators are the skill's unique mandates (T/lock-first
ranking, single-context exception check, override cadence under pressure),
which is exactly where S2 has value and S1 mostly does not.

**Decision:** both arms move to clean-home `opencode run` (protocol updated).
S1 stays as a regression/shape check for skill edits rather than a
discriminating test; S2 carries the behavior claim. Full cycle 2 awaits an
explicit spend approving decision.

## Cycle 1 bottom line (batching claim superseded by cycle 1b)

The skill binds on what an agent faces unprompted (S1: clean inventories,
preserved layout exception, ranked gates) and did not bind under an explicit
user override at first pass (S2: 0/3) — cycle 1b's edit flipped that to 3/3.
V6 sits at 1/6 pending its own evidence-first pass. Control redesign remains
the gate for all baseline claims, S3 needs a redesign or a retirement call,
and multi-turn is the upgrade path for R5/R6/R10.
